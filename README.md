# Локальный индексатор документов

Учебное, но полностью рабочее Streamlit-приложение для локальной индексации документов, семантического поиска и наглядного сравнения фиксированного и структурного chunking.

Документы не передаются внешним API. После первоначальной загрузки открытой модели все вычисления и хранение выполняются локально.

## Возможности

- загрузка PDF, Markdown, TXT и Python через браузер;
- защита от дубликатов по SHA-256 содержимого;
- постраничное извлечение PDF и понятное сообщение для PDF без текстового слоя;
- безопасная нормализация текста с сохранением Markdown и исходного Python-кода;
- fixed chunking по токенам модели с настраиваемым overlap;
- structural chunking по Markdown-заголовкам, Python-функциям, классам и методам, текстовым разделам;
- локальные нормализованные эмбеддинги `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`;
- отдельные FAISS + SQLite индексы для `fixed` и `structural`;
- поиск с фильтром источника и выдачей до 20 результатов;
- просмотр полного текста и всех метаданных чанков;
- сравнение выдачи двух стратегий в соседних колонках;
- статистика, Plotly-графики, Hit@1, Hit@3 и Markdown-отчёт;
- сравнение Baseline, Filtered и Enhanced RAG с Query Rewrite, фильтрацией и reranking;
- диагностика candidate set, причин отсева, score и времени каждого этапа;
- 10-вопросный retrieval benchmark, threshold experiment и отчёт Day 23;
- атомарная запись файлов индекса и проверка соответствия FAISS/SQLite;
- русскоязычные сообщения, файловое логирование и автоматические тесты.

## Архитектура

```text
Файл → loaders → normalization → chunking → Sentence Transformer
                                             ↓
                    manifest.json ← FAISS + SQLite
                                             ↓
                   search → comparison → analytics/report
```

Бизнес-логика находится в `src/`, а `app.py` отвечает только за интерфейс:

- `src/config.py` — пути, модель, поддерживаемые форматы, логирование;
- `src/models.py` — `Document`, `Chunk`, `IndexingResult`;
- `src/loaders.py` — извлечение PDF/Markdown/TXT/Python;
- `src/text_utils.py` — нормализация, хеши и токенизаторы;
- `src/chunking.py` — обе стратегии разбиения;
- `src/embeddings.py` — кешируемая локальная модель и batch encoding;
- `src/storage.py` — FAISS, SQLite, манифест и проверки целостности;
- `src/pipeline.py` — полный конвейер индексации;
- `src/search.py` — семантический поиск;
- `src/evaluation.py` — статистика, контрольные запросы и отчёт.
- `src/retrieval.py` — Query Rewrite, multi-query search, RRF, фильтры и reranking;
- `src/rag.py` — режимы `no_rag`, `baseline_rag`, `filtered_rag`, `enhanced_rag`;
- `src/retrieval_evaluation.py` — retrieval-метрики, benchmark, threshold experiment;
- `src/result_storage.py` — мигрируемое SQLite-хранилище запусков и ручных оценок.

## Требования

- Python 3.11 или новее;
- интернет только для установки пакетов и первоначальной загрузки модели;
- несколько гигабайт свободного места для PyTorch, модели и индексов.

## Установка

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

На Apple Silicon используется нативный пакет `faiss-cpu`. Платные ключи и внешняя база данных не нужны.

## Запуск

```bash
streamlit run app.py
```

Streamlit выведет локальный адрес, обычно `http://localhost:8501`.

1. Во вкладке **Документы** загрузите один или несколько файлов. Демо-набор уже находится в `documents/`.
2. Во вкладке **Индексация** выберите обе стратегии и параметры, затем запустите построение.
3. Во вкладке **Чанки** изучите метаданные и границы фрагментов.
4. Выполните запрос во вкладке **Поиск**.
5. Во вкладке **Сравнение** сопоставьте fixed и structural выдачу.
6. Во вкладке **Аналитика** изучите графики и запустите контрольную оценку.

## Поддерживаемые форматы

| Формат | Извлечение | Структурное разбиение |
|---|---|---|
| PDF | отдельно для каждой непустой страницы | абзацы и короткие заголовки, номер страницы сохраняется |
| Markdown | UTF-8, заголовки и code blocks сохраняются | путь заголовков `H1 > H2 > H3` |
| TXT | строгий UTF-8 | пустые строки и короткие заголовки |
| Python | полный исходный текст без переформатирования | модуль, функции, async-функции, классы и методы через `ast` |

OCR не входит в проект: сканированный PDF без текстового слоя будет отклонён с понятным сообщением.

## Стратегии chunking

### Fixed

Текст токенизируется токенизатором модели и разбивается окнами. По умолчанию размер равен 500 токенам, overlap — 80. Последнее непустое окно сохраняется. Метаданные содержат символьные позиции начала и конца.

### Structural

- Markdown разделяется по заголовкам уровней 1–6, заголовок остаётся в тексте;
- Python разделяется по AST-сущностям; методы получают секции вида `ClassName.method_name`;
- TXT и PDF используют абзацы и похожие на заголовки короткие строки;
- секция длиннее лимита делится токенными окнами с overlap, сохраняя исходное поле `section`.

Structural обычно лучше сохраняет смысловые границы, но создаёт чанки неодинакового размера. Fixed проще и даёт более равномерное распределение. Фактическое качество следует проверять на собственных документах и запросах.

## Формат индекса

Каждая стратегия хранится независимо:

```text
indexes/fixed/
├── vectors.faiss
├── metadata.sqlite
└── manifest.json
indexes/structural/
├── vectors.faiss
├── metadata.sqlite
└── manifest.json
```

`vectors.faiss` содержит `faiss.IndexFlatIP` с нормализованными `float32` векторами. `metadata.sqlite` содержит текст и поля `chunk_id`, `document_id`, `source`, `title`, `section`, `strategy`, `token_count`, `page_number`, `start_position`, `end_position`. `vector_id` — непрерывный первичный ключ и точная позиция в FAISS.

Манифест фиксирует стратегию, модель, размерность, UTC-дату, количество документов и чанков, параметры chunking и длительности этапов. Запись идёт через временные файлы с атомарной заменой.

## Пример поиска

После построения обоих индексов введите запрос:

```text
Как связаны идентификаторы FAISS и SQLite?
```

Приложение покажет similarity score, источник, секцию, страницу, размер и полный текст каждого найденного чанка. Источник можно ограничить фильтром.

## Сравнение стратегий

В `documents/evaluation_queries.json` содержатся 10 контрольных запросов с ожидаемыми источниками и секциями. Кнопка контрольной оценки вычисляет:

- количество, минимум, максимум, среднее и медиану размеров чанков;
- длительность chunking, embeddings и поиска;
- Hit@1 и Hit@3;
- долю чанков с заполненной секцией.

Отчёт сохраняется в `reports/comparison.md`. Демо-набор специально содержит Markdown, обычный текст и Python, чтобы наблюдать различия: fixed формирует равномерные окна, structural сохраняет тематические и программные границы.

Контрольный прогон на демо-наборе с параметрами 500/700 токенов и overlap 80:

| Метрика | fixed | structural |
|---|---:|---:|
| Чанки | 72 | 155 |
| Средний размер | 497.07 | 199.93 |
| Медианный размер | 500 | 207 |
| Hit@1 | 50% | 40% |
| Hit@3 | 80% | 70% |
| Чанки с секцией | 0% | 100% |

На этом наборе fixed чаще находит ожидаемый источник, а structural всегда сохраняет секцию и возвращает более компактный контекст. Конкретные числа зависят от версии модели, оборудования, документов и параметров.

Каталог `documents/` содержит:

## Ограничения

- OCR для сканированных PDF не реализован;
- при первом реальном запуске модель должна быть загружена из Hugging Face;
- `IndexFlatIP` выполняет точный поиск и хранит все векторы в памяти, поэтому для коллекций на миллионы чанков потребуется другой тип FAISS-индекса;
- при изменении исходных документов индекс нужно построить заново;
- качество Hit@k зависит от языка, содержания коллекции и формулировок запросов.

## RAG, фильтрация и локальный reranking

Приложение использует только локальную Ollama и поддерживает четыре режима:

- **без RAG** — LLM получает только исходный вопрос;
- **Baseline RAG** — исходный вопрос → обычный FAISS Top-K → контекст → LLM; Query Rewrite, threshold и reranking отключены;
- **Filtered RAG** — исходный вопрос → широкий FAISS-поиск → similarity threshold → Final Top-K; отдельный reranker отключён;
- **Enhanced RAG** — исходный вопрос и переписанные варианты → FAISS → RRF → threshold → heuristic reranking → ограничение источников → Final Top-K → LLM.

Основное сравнение в интерфейсе — **Baseline RAG против Enhanced RAG**. Обе стороны используют одинаковые документы, индекс, embedding-модель, Ollama-модель, `temperature` и бюджет контекста. Различаются только retrieval-настройки. Для контроля можно отдельно добавить **Filtered RAG** и режим без RAG.

```text
исходный вопрос
  → Query Rewrite
  → поиск по исходному и переписанным запросам
  → дедупликация по chunk_id
  → Reciprocal Rank Fusion
  → similarity threshold
  → heuristic reranking
  → лимит чанков одного источника
  → Final Top-K
  → недоверенный контекст
  → локальная Ollama
  → ответ со ссылками [1], [2]
```

Исходный вопрос всегда участвует в Enhanced Retrieval. Документный контекст передаётся только в пользовательском сообщении и отделяется явными маркерами. URL Ollama ограничен локальными адресами `localhost`, `127.0.0.1` и `::1`.

### Query Rewrite и fallback

Query Rewrite использует тот же интерфейс `LLMProvider`, но отдельный системный промпт. Модель обязана вернуть только JSON:

```json
{
  "search_query": "переписанный поисковый запрос",
  "alternative_queries": ["вариант 1", "вариант 2"]
}
```

JSON валидируется. Пустые, повторяющиеся и совпадающие с исходным вопросом альтернативы удаляются; число вариантов ограничивается настройкой. Слишком длинный текст отклоняется как попытка вернуть ответ вместо поискового запроса. Результат rewrite используется только для поиска и никогда не становится LLM-контекстом.

При тайм-ауте, ошибке Ollama, пустом запросе или невалидном JSON выполняется безопасный fallback: поиск продолжается по исходному вопросу. Причина fallback сохраняется в SQLite и показывается в интерфейсе.

### RRF, similarity и heuristic reranker

Результаты нескольких запросов объединяются по `chunk_id`. Для каждого чанка сохраняются найденные запросы, лучшая similarity и лучшая исходная позиция. Reciprocal Rank Fusion:

```text
RRF(chunk) = Σ 1 / (60 + rank)
```

При равенстве используются similarity, исходный rank и `chunk_id`, поэтому порядок детерминирован.
После fusion берутся первые `Candidate Top-K` уникальных чанков; лимит относится ко всему candidate set, а не отдельно к каждому варианту запроса.

Similarity threshold применяется к исходному FAISS score. Значение на границе проходит фильтр. Чанк ниже порога получает статус `rejected_similarity` с фактическими score и threshold. Такой чанк никогда не передаётся LLM, даже если иначе Final Top-K оказался бы пустым.

Heuristic reranker не загружает дополнительную модель:

```text
semantic_score = (clamp(cosine_similarity, -1, 1) + 1) / 2

final_score =
    0.70 × semantic_score
  + 0.20 × lexical_score
  + 0.10 × metadata_score
```

`lexical_score` — доля значимых терминов вопроса, найденных в тексте чанка. `metadata_score` учитывает имя файла, заголовок и секцию; технические идентификаторы вроде `load_pdf` получают двойной вес. Компоненты не смешиваются до явной нормализации semantic score и сохраняются отдельно.

Доступен `NoOpReranker`, сохраняющий входной порядок. CrossEncoder не является зависимостью и в текущей реализации не требуется.

### Вкладка «Сравнение RAG»

Основные настройки:

- индекс `fixed` или `structural`;
- Baseline Top-K;
- Query Rewrite и число альтернатив;
- Candidate Top-K;
- similarity threshold;
- `Heuristic` или `NoOp`;
- необязательный rerank threshold;
- Final Top-K;
- максимум чанков одного источника;
- бюджет контекста и `temperature`;
- дополнительный режим без RAG.

После сравнения отображаются:

- ответы и фактически переданные источники;
- исходный и rewritten query;
- альтернативные запросы и fallback;
- воронка `FAISS → similarity → reranking → Final Top-K`;
- времена всех этапов;
- исходный и итоговый rank;
- similarity, fusion, semantic, lexical, metadata, rerank и final score;
- статус и причина отклонения каждого чанка;
- полный текст и `chunk_id`.

Статусы: `selected`, `accepted_not_selected`, `rejected_similarity`, `rejected_rerank`, `rejected_source_limit`. Если подходящих чанков нет, генерация с контекстом не вызывается.

Ручная оценка хранит лучший режим, оценки Baseline/Enhanced от 0 до 2, корректность источников, наличие нерелевантных источников и неподтверждённых утверждений, влияние rewrite и комментарий.

### Контрольные вопросы, метрики и threshold experiment

Используются существующие 10 вопросов из `evaluation/questions.json`: запуск, форматы, fixed и structural chunking, согласованность FAISS/SQLite, обработка ошибок, атомарное сохранение, `normalize_vector`, `VectorCatalog.add_many` и неотвечаемый вопрос.

Вкладка **«Оценка RAG»** сравнивает Baseline Top-5 и настраиваемый Enhanced Retrieval. Каждый вопрос сохраняется независимо; единичная ошибка не уничтожает остальные результаты.
Последние benchmark- и threshold-результаты загружаются из SQLite после перезапуска приложения; графики строятся по этим сохранённым данным.

Retrieval-метрики:

- Source Hit@1, Hit@3 и Hit@K;
- MRR;
- Precision@K;
- позиция первого правильного источника;
- число отфильтрованных кандидатов;
- доля нерелевантных чанков;
- доля пустых результатов;
- времена rewrite, filtering, reranking и полного retrieval.

Чтобы измерять именно влияние порога, Query Rewrite в threshold experiment фиксированно выключен; основной Baseline/Enhanced benchmark по-прежнему использует выбранную настройку rewrite.
Threshold experiment принимает произвольный список значений. По умолчанию: `0.20, 0.30, 0.35, 0.40, 0.50`. Для каждого порога считаются Hit@K, Precision@K, среднее число прошедших кандидатов, доля пустых результатов и время. Эксперимент читает индекс и не изменяет его.

Отчёт сохраняется в:

```text
reports/reranking_comparison.md
```

### SQLite-миграция и диагностика

Результаты остаются отдельно от `indexes/*/metadata.sqlite`:

```text
data/results.sqlite
```

При открытии выполняется транзакционная миграция через `PRAGMA user_version = 2`. Она:

- добавляет новые поля `rag_runs` и ручной оценки только при их отсутствии;
- расширяет допустимые режимы `rag_answers`;
- создаёт `retrieval_candidates`;
- не меняет и не удаляет старые запуски Day 22;
- безопасна при повторном запуске.

`retrieval_candidates` хранит source, section, ranks, все компоненты score, status, причину отклонения и matched queries. Полный текст чанка не дублируется: он остаётся в SQLite выбранного индекса.

### Экспорт и безопасный сброс

Экспорт `evaluation/results.json` включает новые настройки и диагностику и записывается через временный файл с атомарной заменой.

Доступны отдельные операции:

- очистить историю сравнений вместе с `retrieval_candidates`;
- очистить benchmark-результаты;
- сбросить все результаты RAG и JSON;
- отдельно удалить индексы.

Обычный сброс использует фиксированный allowlist таблиц. Он не удаляет документы, `evaluation/questions.json`, FAISS, `metadata.sqlite` или модели. Удаление индексов находится в отдельной опасной зоне, требует слова `СБРОС` и затрагивает только заранее определённые файлы выбранной стратегии.
