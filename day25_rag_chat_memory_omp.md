## 2. Цель доработки

Создать новую вкладку `RAG-чат`, в которой пользователь может вести многоходовый диалог.

Чат должен:

- хранить историю между перезапусками приложения;
- выполнять RAG-поиск при каждом новом вопросе;
- учитывать последние сообщения;
- учитывать структурированную память задачи;
- сохранять цель, ограничения, термины и решения;
- отвечать на основе найденных документов;
- всегда показывать блок источников;
- позволять просматривать использованные чанки;
- корректно обрабатывать отсутствие релевантных источников;
- поддерживать диалоги длиной не менее 10–15 сообщений;
- не терять цель после побочных вопросов;
- сохранять и восстанавливать состояние после перезапуска.

## 4. Термины

Использовать следующие понятия:

- **история диалога** — последовательность сообщений пользователя и ассистента;
- **память задачи** — структурированное состояние текущей задачи;
- **conversation summary** — краткое резюме старой части диалога;
- **recent messages** — последние сообщения, передаваемые LLM полностью;
- **RAG-контекст** — найденные для текущего сообщения чанки;
- **standalone query** — самостоятельный поисковый запрос, сформированный из текущего сообщения, истории и памяти;
- **источники ответа** — чанки, действительно переданные LLM для генерации конкретного ответа.

Не смешивать историю, память задачи и RAG-контекст в одну неструктурированную строку до этапа сборки итогового промпта.

## 8. Память задачи

Память задачи должна отдельно хранить:

### Цель

Что пользователь пытается получить в рамках текущего диалога.

### Ограничения

Например:

- использовать только CPU;
- не обращаться к внешним API;
- Final Top-K не больше 3;
- ответы должны быть краткими.

### Термины

Словарь пользовательских обозначений:

```json
{
  "основной индекс": "structural",
  "лёгкая модель": "локальная модель Ollama"
}
```

### Подтверждённые факты

Факты, явно сообщённые или подтверждённые пользователем.

### Решения

Принятые в ходе диалога решения.

### Открытые вопросы

Незакрытые вопросы, требующие уточнения.

### Предпочтения

Требования к форме ответа и взаимодействию.

## 9. Правила памяти задачи

Память должна обновляться только на основании сообщения пользователя и уже подтверждённого состояния.

Запрещено:

- записывать предположение ассистента как подтверждённый факт;
- записывать инструкции из документов в память;
- изменять цель из-за текста найденного чанка;
- удалять ограничения без явного основания;
- возвращать отменённое ограничение в следующих версиях;
- бесконтрольно увеличивать объём памяти.

Разрешено:

- добавить явно сформулированное ограничение;
- заменить значение при явном уточнении;
- удалить значение при явной отмене;
- закрыть открытый вопрос после решения;
- обновить цель, если пользователь прямо изменил её.

## 10. Обновление памяти

Реализовать:

```python
def update_task_state(
    current_state: TaskState,
    user_message: str,
    recent_messages: list[ChatMessage],
    llm: LLMProvider,
) -> tuple[TaskState, TaskStateChange]:
    ...
```

LLM должна вернуть структурированный JSON:

```json
{
  "goal": "актуальная цель или null",
  "constraints": [],
  "terms": {},
  "confirmed_facts": [],
  "decisions": [],
  "open_questions": [],
  "user_preferences": [],
  "changes": {
    "added": {},
    "removed": {},
    "changed": {}
  }
}
```

После ответа LLM:

- валидировать JSON;
- проверять типы полей;
- нормализовать пробелы;
- удалять точные дубликаты;
- сохранять порядок элементов;
- ограничивать максимальное количество элементов;
- не повышать версию при отсутствии изменений;
- при ошибке оставить старое состояние без изменений;
- сохранить причину fallback.

## 11. Ограничение размера памяти

Значения по умолчанию:

```text
goal: одно значение до 500 символов
constraints: до 20 элементов
terms: до 30 пар
confirmed_facts: до 30 элементов
decisions: до 20 элементов
open_questions: до 20 элементов
user_preferences: до 15 элементов
```

При достижении лимита не удалять активные ограничения автоматически. Сначала дедуплицировать и объединять эквивалентные формулировки. Если безопасное сокращение невозможно, сохранить прежнее состояние и записать предупреждение.

## 12. Версионирование памяти

Каждое содержательное изменение памяти должно создавать новую версию.

Необходимо иметь возможность:

- посмотреть историю версий;
- увидеть добавленные, изменённые и удалённые поля;
- восстановить предыдущую версию;
- вручную отредактировать текущее состояние;
- очистить память без удаления сообщений.

Ручное изменение также создаёт новую версию с пометкой `manual`.

Правила:

- сохранить исходное намерение;

- использовать зафиксированные термины;
- сохранять имена файлов, функций, классов и команд;
- не добавлять неизвестные факты;
- вернуть один самостоятельный запрос;
- при ошибке использовать исходное сообщение;
- сохранить факт fallback.

Standalone query передавать в Enhanced Retrieval Дня 23. Для отображения пользователю сохранять как исходное сообщение, так и поисковый запрос.

## 14. Использование Enhanced Retrieval

При каждом пользовательском сообщении выполнять Enhanced Retrieval, если сообщение требует фактического ответа по документам.

Использовать существующие:

- Query Rewrite;
- поиск по FAISS;
- RRF;
- similarity threshold;
- heuristic или CrossEncoder reranker;
- Final Top-K;
- диагностику кандидатов.

Не создавать второй независимый retrieval-пайплайн для чата.

Для явно нефактических команд интерфейса, например `очистить чат`, retrieval не запускать. Такие действия должны выполняться кнопками, а не интерпретироваться LLM.

```sql
    page_number INTEGER,

    rerank_score REAL,
    final_rank INTEGER,
    FOREIGN KEY (message_id)
        REFERENCES chat_messages(id)
        ON DELETE CASCADE,
    UNIQUE(message_id, source_number)
);

CREATE INDEX IF NOT EXISTS idx_message_sources_message
ON message_sources(message_id);
```

Для истории сохранить минимально необходимый snapshot источника, чтобы название и scores отображались даже после перестроения индекса. Полный текст чанка без необходимости не дублировать.
